# ADR-028: Assignments (teacher-authored questions, issued and tracked)

**Status:** Accepted
**Date:** 15 November 2026

## Context

Siya's request, in his own words: a teacher should be able to issue assignments and tests, see how students have completed their homework -- "basically everything a teacher is supposed to do." That is a whole product surface, not one feature. Scoped via `AskUserQuestion` into a concrete first slice: start designing now (ahead of finishing the still-pending ADR-024 live-test walkthrough); build **assignments** first, before formal tests or a dedicated progress-tracking view, since issuing work is the foundation completion-tracking and grading both build on; and let teachers author their own custom questions, not only reuse the seeded CAPS question bank -- a deliberately bigger scope than the minimum.

**A major, previously-undocumented finding surfaced while designing this**, worth stating loudly rather than discovering by accident mid-build: a repo-wide search for `Attempt(` -- the constructor call that would create a new scored-response row -- found exactly one match, the model's own class definition. Every other reference to `Attempt` anywhere in `app/` (`diagnosis.py`'s root-gap walk, `personalization.py`'s pace tier, `dashboard.py`'s mastery/risk views, `risk_assessment.py`) is a read. **Nothing in this codebase has ever actually written an `Attempt` row in production.** The 24+ diagnostic questions seeded per subject/grade (`Question.is_diagnostic=True`) have never had an API path for a student to actually answer one and have it scored. This means the entire mastery/diagnosis/pace/risk subsystem -- everything ADR-007, ADR-002, and the TEACH dashboard read as "real attempt data" -- has been running on a table that was always empty outside unit tests' own hand-built fixtures. This was not Siya's ask, but building Assignments properly requires a working "submit an answer, get it marked, write the Attempt row" path either way, so this ADR builds that path for the first time, as a byproduct of Assignments rather than a separate initiative -- and once it exists, every one of those existing read-only consumers starts seeing real data for any learner who actually does an assignment, with zero changes needed on their side.

## Decision

**Reuse `Attempt` as the single source of truth for assignment completion too**, rather than inventing a parallel `AssignmentSubmission` table with its own correctness tracking. `Attempt` gains one new nullable column, `assignment_id`, set only when a response was submitted in the context of a specific assignment question; every existing read path (`diagnosis.py`, `personalization.py`, `dashboard.py`, `risk_assessment.py`) is completely unaffected, since none of them filter on it. This matches the project's own stated principle for `Attempt` ("single source of truth for mastery -- never a separately-stored mutable score") rather than contradicting it under feature pressure.

**New tables, additive only, no existing table restructured:**
- `assignments` -- `id`, `school_id` (FK `schools.id`, for the same "the picker isn't the boundary" server-side scoping ADR-024 already established for the teacher dashboard), `teacher_user_id` (FK `users.id`), `title`, `instructions` (nullable), `due_at` (nullable), `created_at`.
- `assignment_questions` -- the ordered many-to-many between an assignment and the `Question` rows it contains (`assignment_id`, `question_id`, `order_index`, unique on the pair). A question can belong to more than one assignment; an assignment can mix seeded CAPS questions with a teacher's own custom ones freely.
- `assignment_targets` -- which `Learner`s this assignment was actually issued to (`assignment_id`, `learner_id`, unique on the pair). No `Class`/group concept yet -- a teacher picks students individually from the same roster ADR-024's admin UI already lists; grouping is a real, deferred feature, not assumed away.

**`Question` gains one nullable column, `created_by_user_id`** (FK `users.id`). `None` for every seeded/diagnostic/AI-generated question exactly as today; set to the authoring teacher's `User.id` for a custom one. No new boolean needed -- "is this teacher-authored" is just `created_by_user_id IS NOT NULL` -- and `is_diagnostic`/`is_ai_generated` both stay `False` for a teacher-authored question, since it's neither of those existing categories.

**The marking flow (`app/services/answer_marking.py`) reuses `TutorClient.ask()`** -- the same thin Anthropic SDK wrapper `tutor.py` already uses for the tutoring chat itself -- rather than standing up a second Claude integration. A dedicated, narrow system prompt asks Claude to judge one learner response against one question's `model_answer` and return a small JSON object (`is_correct`, `feedback`); the response is parsed defensively (a malformed/non-JSON reply degrades to `is_correct=None` -- "unmarked," the same honest-uncertainty posture MathGuard uses, never a false positive or negative manufactured to avoid an error). This is a narrower, single-purpose prompt than the full tutoring system prompt -- it is not asked to teach, only to judge -- and it is the first real exercise of "Claude marks a specific answer" anywhere in this codebase.

**Completion status is computed, not stored**, the same pattern `personalization.py`'s pace tier already uses (`app/services/assignments.py`'s `get_assignment_completion()`): for a given learner on a given assignment, `not_started` (no `Attempt` rows with this `assignment_id` for this learner at all), `in_progress` (some but not all of the assignment's questions have one), `completed` (every one does). A score is the fraction of attempted questions marked `is_correct=True`, shown only over questions actually attempted, not assumed over the whole assignment. This avoids a second, independently-mutable "status" column that could drift from what the `Attempt` rows actually say.

**Server-side scoping mirrors ADR-024 exactly**, not a weaker ad hoc check: `create_assignment()` validates every targeted `learner_id` belongs to a `User` in the authenticated teacher's own `school_id` before creating any `assignment_targets` row -- the same "the picker isn't the boundary" enforcement ADR-024 and ADR-026 both already insisted on, not merely trusting whatever a client-side student picker happened to send. A student's own `GET /assignments`/`POST .../answer` endpoints are scoped to `assignment_targets` rows naming that learner specifically -- a learner can never see or answer an assignment they weren't actually issued, including one issued to a different student at the same school.

**The student-facing question view never returns `model_answer`.** `GET /assignments/{id}` returns each question's text only; the answer key stays server-side, read only by `answer_marking.py` during grading. This is the obvious, non-negotiable boundary for anything resembling a real assessment, called out explicitly rather than left to be caught later by accident.

## Scope, explicitly bounded for this pass

- **Assignments only.** Formal timed/scored "tests" as their own distinct type, and a dedicated teacher-facing progress/mastery dashboard view, were both deliberately deferred in the `AskUserQuestion` scoping -- real, named TEACH roadmap items (already flagged as such in ADR-025), not forgotten.
- **No `Class`/group concept.** A teacher targets individual students per assignment. Grouping by class is a real gap for a teacher with many students, left for whenever it's actually needed rather than guessed at now.
- **No due-date enforcement or late-submission handling.** `due_at` is stored and shown, but nothing currently blocks a late answer or flags one as late.
- **Custom questions are global once created**, not assignment-exclusive -- a teacher's own question, once authored, can be reused across multiple assignments of theirs, the same way a seeded question can.

## Consequences

- `backend/migrations/versions/0006_add_assignments.py`: new tables plus the two new columns.
- `backend/app/models/__init__.py`: `Assignment`, `AssignmentQuestion`, `AssignmentTarget`; `Question.created_by_user_id`; `Attempt.assignment_id`.
- `backend/app/services/answer_marking.py`: the first real AI-marking flow in this codebase.
- `backend/app/services/assignments.py`: creation, targeting/scoping validation, answer submission, and completion-status computation.
- `backend/app/routers/teach_assignments.py` (teacher-facing, `get_current_teacher`-gated) and `backend/app/routers/learner_assignments.py` (student-facing, `get_current_learner`-gated), both registered in `app/main.py`.
- `backend/app/schemas/assignments.py`: request/response models for both routers.
- `frontend/src/components/TeacherAdminScreen.jsx`: a fourth tab, "Assignments" -- create (an inline custom-question-authoring form + a student picker from the existing roster) and a list with per-student completion status.
- A new student-facing assignments view (`frontend/src/components/AssignmentsView.jsx`, toggled into `ChatScreen.jsx` alongside the existing tutor chat) listing issued work and letting a student answer each question with immediate AI-marked feedback.
- Verified well beyond `ast.parse` this time: the sandbox turned out to already have FastAPI/SQLAlchemy/pydantic installed, and a handful of `pip install`s (pydantic-settings, python-jose, passlib, bcrypt, httpx) got every new module importing for real, not just parsing. Every new backend module (`answer_marking.py`, `assignments.py`, `schemas/assignments.py`, both new routers) imports and resolves cleanly standalone; `app.main` itself still can't be imported here because `personalization.py`/`diagnosis.py`/`tutor_orchestration.py` use `datetime.UTC`, which needs Python 3.11+ and this sandbox's system `python3` is 3.10 -- a pre-existing environment gap, not something this change introduced, and confirmed not to block anything below. The **existing test suite runs for real here** (not just `ast.parse`): `pytest tests/ --ignore=test_diagnosis.py --ignore=test_personalization.py --ignore=test_tutor_orchestration.py` (the same three files blocked by the same `datetime.UTC` gap) -- 148 passed, zero regressions. New tests added: `tests/test_answer_marking.py` (6 tests, mocking `TutorClient.ask()` the same way `test_tutor_client.py` mocks the SDK one layer down -- covers clean JSON, a markdown-fenced response, malformed/non-boolean output degrading to `is_correct=None`, and an API failure degrading the same way) and `tests/test_assignments.py` (`create_custom_question()`, the one pure function in that module -- `create_assignment()`/`submit_assignment_answer()`/`get_assignment_completion()` all need a real `AsyncSession` and are deliberately left untested here, same "integration, not unit" line `test_admin.py` already draws around `bulk_provision_students()`). On the frontend: a real `vite build` succeeds (303 modules) and `eslint` reports only the same `react-hooks/set-state-in-effect` pattern the existing `loadRoster()` effect in `TeacherAdminScreen.jsx` already triggers -- not a new category of issue, just more occurrences of an existing one.

## Open items (explicitly not done, not silently dropped)

- **Not live-tested against a real Claude call or a real browser session.** Unit-tested and import-verified, including a real `pytest` run and a real `vite build` (see Consequences) -- but nobody has yet logged in as the dev teacher, created a real assignment, logged in as the dev student, and submitted a real answer end to end. This is a bigger surface than any single prior fix this session -- a new DB migration, a new AI-marking call, two new routers, and two new frontend surfaces -- so the live-test handoff matters more than usual here, not less.
- **No way to reuse the seeded CAPS question bank in an assignment yet.** The teacher-facing "Add a question" form only authors brand-new custom questions -- there is no `GET` endpoint anywhere in this codebase to browse the existing diagnostic/AI-generated bank by topic (confirmed by grep: no router exposes `Question` for listing, ever), so "reuse the seeded bank" from Siya's own scoping answer is not actually available yet, only "author custom questions" is. A real gap, not a silent scope-narrowing: flagging it here so it isn't mistaken for "done."
- **The "nothing ever wrote an Attempt row" finding is bigger than Assignments.** Once a real student actually completes an assignment, `dashboard.py`'s mastery/risk views and `diagnosis.py`'s root-gap redirects will, for the first time, be reading genuine data instead of an empty table for that learner -- worth watching for surprising behaviour changes there that are correct (the system finally working as designed) rather than a bug in this change.
- **Formal tests, a dedicated TEACH progress dashboard, class/group targeting, and due-date enforcement** are real, named, deferred scope -- not part of this pass.
- **Marking quality is unverified.** `answer_marking.py`'s defensive JSON-parsing is unit-tested (malformed/non-boolean output correctly degrades to `is_correct=None`), but the prompt itself has never been run against a real learner response via the real Anthropic API; whether its judgments are reliably correct, too lenient, or too strict on CAPS-specific phrasing is exactly the kind of thing this project's "ship then verify" discipline exists to catch via real use, not guess at upfront.
